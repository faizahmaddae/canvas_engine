# Paint/Draw Tool Audit — August 2026

> Scoped exclusively to the paint/draw tool (not the toolbar system generally).
> Produced 2026-08-18 on `feat/command-scope-contract`, HEAD `1f4803b` ("the
> dock says which stroke it edits, next or selected"), in response to the
> programmer's own complaint that the paint code is "complex and confusing to
> work in" and that the paint UX is weak. Every finding below is drawn from a
> pool that was adversarially re-verified against the current tree — citations
> were re-read byte-for-byte at HEAD, not trusted from the originating pass.
> 40 findings survived verification (confirmed or adjusted); 1 was refuted
> outright and is recorded in the appendix rather than dropped. Read-only: no
> fix in this document has been applied to the code. Severities follow the
> July convention: P0 breaks core editing or data (none found in this scope);
> P1 major flaw worth redesign; P2 consistency/polish; P3 nit.

## Status of the four July "check if still open" items

The July 2026 toolbar audit (`docs/toolbar-redesign-audit-2026-07.md`, commit
`8a612ec`) flagged four paint-specific issues. This audit re-checked all four
against HEAD as a byproduct of the findings below — none of the 40 verified
findings reopens any of them, so all four are **reconfirmed fixed**, with one
caveat:

- **`paint-tool:committed-layer-style-immutable`** (blur/sides/dash uneditable
  after commit) — fixed. `setBlurRadius`/`setPolygonSides`/`selectLineStyle`
  all branch on `selectedPaintLayer()` to restyle a *committed* layer's
  blur/sides/dash today (paint_tool_controller.dart:471-490, 536-548,
  557-570; see paint-tool:dual-target-branch-duplicated-not-factored below).
  `UpdatePaintStyleCommand.apply()` writes `sides`/`blurSigma` unconditionally
  (paint_commands.dart:74-103; see paint-tool:sides-blursigma-command-codec-
  kind-gating-asymmetry).
- **`paint-tool:any-tap-exits-mode`** (any canvas tap ejects paint mode) —
  fixed. `_handleTapRelease` (paint_gesture_surface.dart:327-341) only erases,
  commits a dot, or no-ops; it never calls `dismissActiveEditing` or otherwise
  exits the mode. It has, however, been replaced by a different, still-open
  problem: a tap on an *existing* stroke while armed doesn't select it either
  — see paint-tool:tap-to-select-existing-stroke-unreachable-while-armed and
  paint-tool:no-lightweight-deselect-to-restyle below. The old bug (unwanted
  exit) is gone; the underlying "a tap while armed does nothing useful to an
  existing stroke" gap is not.
- **`paint-tool:god-file-not-decomposed`** — fixed for the file it was raised
  against: `paint_mode_toolbar.dart` is 281 lines at HEAD (verified via
  `wc -l`), down from 1439, split into `paint/{application,presentation/
  bodies}`. However, `paint_tool_controller.dart` is now 681 lines
  concentrating panel/slot lifecycle, tool arming, style defaults, restyle
  dispatch, the scope predicate, four preview/commit channels, scaling math,
  and a view provider — see paint-tool:controller-681-lines-eleven-
  responsibilities below. The complexity that used to live in one god
  *presentation* file has substantially relocated to one god *application*
  file; "decomposed" is true of the file the July finding named, not of the
  module's complexity budget as a whole.
- **`canvas-viewport:paint-mode-has-no-canvas-navigation`** — fixed. Two-
  finger sequences no longer block viewport navigation (see paint-tool:two-
  finger-interrupt-asymmetric-silent-outcomes below, which examines what a
  second finger does today rather than whether it's blocked at all). The
  outcome itself is now asymmetric and silent, but navigation during paint
  mode is genuinely reachable.

## If you fix three things first

- **`paint-tool:scope-unnamed-fifth-scope`** (plus `next-stroke-scope-violates-contract-section-10` and `scope-predicate-duplicated-five-times`) — this is the root cause underneath most of the rest: an undocumented, ad hoc "next-stroke defaults vs. editing-stroke" scope, re-derived five separate ways because it was never named once.
